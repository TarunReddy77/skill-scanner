# M1 spec: whole-folder scanner and labeled benchmark

## Problem Statement

The scanner today reads only a skill's SKILL.md, returns a plain malicious/benign verdict with free-text quotes, and is checked against 10 hand-made, single-file samples. That is too small and too easy to say anything honest about how well it works. Real skills are folders with scripts and other files, attacks come in different kinds, and a score on 10 samples tells nobody much. A reader (a recruiter, an engineer, or Tarun himself) cannot answer "how good is this scanner, on what, and how do you know?"

## Solution

Extend the scanner to read whole skill folders, report what kind of attack it found and where, and measure it on a larger public benchmark with a held-out test split. The benchmark is labeled by a jury of three LLMs (plus trusted labels from published research datasets where they exist), and every number is reported with its counts and ranges. Scanning of real malicious samples happens only after a verified sandbox exists. Until then, the benchmark uses inert placeholder malicious samples.

## Changes to the kickoff brief

The brief (M1-skill-scanner) lives in a private planning repo and is not edited. These decisions from the grilling session replace what it said:

- **Malicious samples are no longer synthetic-only.** The brief said "public skills (benign) plus Tarun's own synthetic malicious samples". Now: Phase 1 uses inert placeholder malicious samples; Phase 2 adds real malicious samples from published research datasets, only after the sandbox checks pass, a license check, and Tarun's approval of the sample counts and cost.
- **Labeling is no longer done by a human.** The brief had open question 6 "who labels" with Tarun as the implied labeler. Now: a jury of three LLMs from different model families (none is the scanner's model) labels by majority vote. Verified labels from research datasets win over the jury. Tarun writes the category definitions and labeling rules, and approves the rules, but does not label samples one by one.
- **Malicious samples are public.** Tarun wants them visible to recruiters, except where a dataset's license forbids redistribution (then the repo holds a pointer: ID, hash, source link).
- **A val split is added in Phase 2.** M1 has `dev` and `test`. In Phase 2, `dev` is split in two (`dev` and `val`). `test` stays untouched.
- **Benign sources are public skill datasets**, not the skills used as tooling for this project.

## Implementation Decisions

**Attack categories (v1).** Six categories, each with a one-line definition that Tarun finalizes:
- data-exfiltration: sends the user's files, code or conversation to a place the user did not choose.
- credential-access: reads or collects secrets that the stated job does not need.
- hidden-instructions: tells the agent to hide things from the user, ignore their rules, or act without being asked (prompt injection).
- destructive-or-persistent-ops: deletes or overwrites data, or plants something that keeps running.
- remote-code-fetch: downloads and runs unreviewed code from the internet.
- obfuscation: hides what the skill really does.

In v2 the categories are aligned with the Snyk ToxicSkills and NVIDIA SkillSpector taxonomies for wider coverage.

**Where "malicious" starts.** A skill is malicious if it does something the user would object to if they knew, and its text hides or misdescribes it. Strong abilities that are openly described are benign. A skill with several problems gets one primary category.

**Verdict.** The verdict is `malicious` or `benign` (no "suspicious" state), plus the primary category (empty when benign), evidence as a list of file, line and quote, a short reasoning, and a confidence value. Confidence is recorded but not used for decisions in M1. A separate scan status, set by the scanner and never by the model, can mark a scan `unscannable`. An `unscannable` scan counts as a failed scan and never as benign.

**Scanner tools.** Two tools only: list the files in the skill folder, and read one file. Reads are confined to the skill folder, refuse symlinks, and execute nothing. There are no search tools and no pre-checks before the model in M1 (planned for v2). Reading a file over 100 KB, or scanning a folder over 500 KB in total, raises a clear "too large to be scanned" error. Nothing is silently shortened.

**Framework independence.** Tools, prompts, schemas, the dataset loader and the scorer stay plain modules that do not depend on the agent framework. The framework only runs the agent loop. The model ID stays configurable. The scorer stays callable from CI.

**Sandbox.** Three layers.
1. Code rules: no run or shell tool, path confinement, no symlinks.
2. A local container with no network, a read-only copy of the sample, a non-root user and no cloud credentials. It holds only the two read tools. The model loop and Bedrock calls stay outside and talk to the container over a pipe. Docker availability is checked first.
3. A harmless canary skill that tries network access, reading a system file and escaping with `../`. Real malicious samples stay blocked until all canary attempts fail.

A managed cloud sandbox is out of scope here and left for M6.

**Dataset layout.** Each skill lives in its own folder under a neutral ID, with no label in the path. One labels file has a line per skill: id, label, category, reason, source, license, split, status, and the jury votes. The existing 10 samples are moved in with history kept.

**Sources and phases.**
- Phase 1: inert placeholder malicious samples (reserved safe domains only, inert payloads, no weaponized code) plus benign skills from public datasets, license-checked per skill. About 60 skills first (about 30 benign and 30 malicious, 5 per category) to prove the pipeline, then growth toward about 200 (about 100 benign, about 100 malicious, about 15 per category) after cost approval. At least 20% of benign skills are hard negatives.
- Phase 2: real malicious samples from published research datasets (candidates: MalSkillBench, Liu et al. USENIX Security 2026, SkillScan, SkillsMetric), only after the sandbox canary checks pass, a license and availability check, and Tarun's approval of the exact sample counts per dataset and the cost estimate. Where a license forbids redistribution, the repo holds a pointer (ID, hash, source link) in place of the file. Public malicious files carry a safety README and no executable bits.

**Labeling.** A separate command runs a jury of three model families, none of them the scanner's model. Judges see the whole folder as text only, with no tools, and return a label, a category and a reason. The majority label wins. 3-0 is marked unanimous and 2-1 is marked contested. All votes and reasons are stored. Verified labels from research datasets win over the jury. The data card says these labels are model opinions and notes possible training-data contamination. The judge model IDs are chosen after checking what is available in the Bedrock region in use.

**Splits.** Each skill is assigned `dev` (70%) or `test` (30%) once, by a fixed rule on its ID, with skills from the same source or template kept together and every category present in both. The test split is for final numbers only: using it prints a warning and logs a run count. In Phase 2, `dev` is split in two (`dev` and `val`) and `test` stays untouched.

**Scoring and evaluation.** Reported: per-category recall and precision, false positive rate on benign skills, share of `unscannable` scans, average tokens and time per scan. Each rate shows its counts and a 95% range, and a category with fewer than 10 test samples is marked "too few to trust". There is no pass/fail target in M1. The evaluation command takes a split choice (dev, test or all; default dev), a label filter (unanimous or all), and a model ID (default Amazon Nova Lite). It saves a JSON file for M2's CI check, and runs stay visible in Langfuse. The jury labeling is not part of the evaluation command.

**Cost and safety rules.** Every run that costs money (scans, jury runs) needs Tarun's yes, with the AWS profile, region and rough cost stated first, using current Bedrock prices. This follows the repo's CLAUDE.md.

## Testing Decisions

**What a good test looks like.** It checks behavior from outside (what goes in, what comes out) and not how the code does it. It runs with no network and no paid model calls.

**Where we test (three places).**
1. The file tools, against a temporary folder: listing and reading work; `../` is refused; symlinks are refused; a file over 100 KB raises the "too large" error; a folder over 500 KB does too.
2. Labels to scores: the dataset loader and the scorer, given a tiny made-up dataset with fixed pretend scanner answers. Checks the split rule and grouping, per-category recall and precision, false positive rate, `unscannable` counting, and the "too few to trust" mark. The same fixture supports the hand-check of the math on about 10 skills.
3. The sandbox: the canary skill's attempts at network access, reading a system file and escaping with `../` must all fail.

The verdict format gets plain validation tests (benign has no category, evidence has file, line and quote, confidence is between 0 and 1).

**Not tested automatically.** Real model calls cost money and vary from run to run. One real-model test exists but is off by default and runs only when asked.

**Prior art.** The repo has no tests yet. The existing evaluation code already computes accuracy, false negative rate and false positive rate, and is the starting point for the scorer.

- Comparing multiple models (M3).
- Defending the scanner against attacks on itself (M4).

- Aligning categories to the Snyk and NVIDIA taxonomies (v2).
